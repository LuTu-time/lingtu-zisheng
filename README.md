# 灵途自生 · 世界观生成引擎

写实底层逻辑世界观生成引擎。依据题材标签自动装载世界规则模块，在真实的社会、资源、人际运行逻辑下推演出可用的世界观、剧情事件与社会矛盾。

**当前状态**：**P0–P3 四个阶段的验收标准全部满足（107/107 模块落地）**。历史不可改写的四重保障已落地并通过验证；可变状态表另加「状态封印」以检出绕过事件的篡改；叙事后端本机默认、云端可选。零第三方依赖，纯标准库。

> **底层法则：事件产生了，就不能修改。** 这是真实世界的运行法则，也是整个项目的底线——「世界自己长出故事」成立的前提，是过去真的发生过、且不能被回头抹掉。

桌面入口是 `desktop.py`；当前增量打包版位于 `out/LingtuDesktop-Housing-20261016/LingtuDesktop-Housing-20261016.exe`，压缩包为 `out/LingtuDesktop-Housing-20261016.zip`。旧版本仍保留。此版内置 **107/107 模块全部落地的引擎（P0 内核 12 + P1 社会骨架 37 + P2 题材扩展 55 + P3 输出交互 3）**，包含入世页、小说写作台、世界观察台（含时间线存档/快照分支/作者干预）与 TXT 设定候选确认。需保留同目录的 `_internal` 文件夹。双击程序打开独立应用窗口，不需要手工启动浏览器或网页服务。默认使用程序旁的 `worlds/desktop.db`：第一次启动新建世界，后续启动继续使用，不会覆盖项目里的 `db/play.db` 或 `db/world.db`。窗口关闭后，应用自己的本机服务随之停止。

从已有存档进入：`LingtuDesktop-P2Full-20261016.exe --db "D:/Projects/lingtu-zisheng/db/play.db"`。该选项只接受已存在且历史校验通过的存档；若 `play.db` 同时被原网页服务使用，先关闭原服务，避免双进程同时写入。依赖本机 Microsoft Edge WebView2 运行环境。Ollama 对话功能仍需本机模型服务；模型不可用时，世界模拟和手写章节不受影响。

源码运行（需要安装 `pywebview`）：`python desktop.py`。自检但不打开窗口：`LingtuDesktop-Housing-20261016.exe --check`。自检会读取世界状态、三个页面及快照列表，不推进世界。复现打包（在已安装 pywebview 和 PyInstaller 的 Python 环境中）：`python tools/build_desktop.py --name LingtuDesktop-NextVersion`；构建名不能重用，旧交付不会被覆盖。桌面壳复用当前入世、写作、人物素材及世界推演界面。

## 浏览器平台（本机运行）

使用现有 Python 标准库，无需安装第三方依赖。首次启动会建立独立于 `db/world.db` 的 `db/play.db` 示例世界：

```bash
python platform.py --new-world
```

浏览器打开 `http://127.0.0.1:8765`，首页为**入世角色**：你亲自填写姓名、年龄、身份和目标，以到访者身份进入当前世界。可拜访村民、帮助采薪，或与村民交谈；交谈由本机 Ollama 模型根据目标村民的档案、记忆、关系和当前世界状态生成回应。所有行动都追加为不可改写事件，重启后身份和经历仍在。每个世界只允许建立一位入世角色，不能事后替换。入世者不算村民劳动力，避免打乱原人口生产模型。模型只负责语言表达，不负责决定世界事实、资源变化或历史事件；模型失败时不会写入半截事件。

`http://127.0.0.1:8765/write` 为**小说写作台**：支持粘贴或选择本地 TXT（按行拆为候选）逐条确认设定；预览不写库，确认时追加不可改写的确认事件并保存已确认设定。数据库触发器保护已确认设定及结构化取值，旧库存档打开时非破坏性补装。另可填写对象、属性、取值确认结构化设定；同一对象和属性若已有不同取值，则在发事件前拒绝并指出已有设定编号。年度纪事按真实事件列出收成、物价、征粮、人口与势力结算的依据编号。自由文本目前仅拒绝完全相同的重复文本，不会自动识别语义矛盾，也不从任意小说段落可靠抽取人物关系。点击人物查看其当前目标与参与的真实事件，直接引用人物经历到章节，或切回“全部事件”并逐页查看更早的历史；重新打开章节会按事件编号补取旧引用摘要；人物记忆是主观视角，不等于历史事实。选人及切换事件不会清空未保存正文、备忘或已有引用。写正文与伏笔备忘、保存和修改章节。章节草稿保存在同一 SQLite 存档的 `chapter_draft` 表中，允许修订；引用只保存事件编号，绝不修改既有事件。多窗口编辑时使用版本号阻止旧窗口覆盖新内容。章节接口允许较长的 JSON 请求体，正文仍由后端限制在 20 万字，备忘限制在 2 万字；其他操作仍维持较小的请求上限。引用事件后，可点击“从引用事件生成草稿”，由本机 Ollama 生成约 150~300 字的可修改中文段落；生成结果只进入编辑区，必须由作者核对后手动保存，不会自动写入章节或世界历史。章节还支持**一键导出全书**（Markdown / 纯文本）：`GET /api/chapters/export?format=md|txt`，写作台左上角「导出 MD / TXT」按钮即下载；导出是只读的，带 `Content-Disposition` 附件名，绝不改变任何记录。设定区还支持**从 TXT 原文抽取候选人物/地点**（`POST /api/import/preview` 只读预览，逐条或全部经 `POST /api/import/commit` 确认写入），以及**设定三态**展示与「推断→作者确认」一键提升。抽取到的人物还可**一键建成世界角色**（`POST /api/import/cast`）：作为具名角色加入名册、参与记忆/关系/自主行为，每次引入写一条不可改写事件；与「入世角色」同例，具名个体与抽象人口分开统计，故不改变人口与经济分配。还能抽出**候选人物关系**（称谓式「A是B的师父」+ 同现式「A与B有仇」，映射为恩/怨/爱/attitude 与初步强度），经确认写成角色间 `relation`（有向、双向各一条，`POST /api/import/relate`）；需双方都已建角，对不上的自动跳过。

`GET /api/chronicle/annual?year=1` 返回只读年度事实及每项证据事件编号；`GET /api/canon` 列出设定，`POST /api/canon/preview` 预览候选，`POST /api/canon` 逐项确认（结构化请求体示例：`{"subject":"古桥","attribute":"建造年代","value":"三百年前","source":"author"}`），确认后不允许回写已发生的历史。现有旬末粮价、结余征粮与粮食借贷形成第一版社会经济链。观察页可从村民势力公仓借粮，借据本金、到期日与余额持久化；每旬按余额计息 1%，到期后仅使用超过按在村人口和单人日耗计算的 10 日口粮的存粮偿还，偿还粮食转回放款势力公仓；不足时记录逾期，不扣成负数。放款、计息、逾期和偿还都追加事件并进入年度纪事证据列表。旧库存档首次调用借贷接口时自动创建借据表，不重建存档。该增量不代表 P1 的借贷市场、多主体贸易、地权等能力已全部落地。

`http://127.0.0.1:8765/simulation` 是次级的**世界素材推演**页：查看状态、村民经历、记忆、关系与事件因果，推进 1/5/10/30 日，或拨粮/植树干预。每日结算包含第一版规则自治：村民可依据需求、目标、记忆与关系自发互助、求助、争执或交往；目前仍是低频、双人交往，并非开放式自主社会。再次运行 `python platform.py` 会继续使用同一个存档；用 `Ctrl+C` 停止服务。

观察页可为**当前存档**创建安全快照，再从快照创建独立分支。接口为 `GET/POST /api/snapshots` 与 `POST /api/branches`；创建时只传显示名称及快照 ID，不能指定输出路径。分支创建后**不会自动切换当前世界**：观察页可从已登记分支列表显式切换，并可返回原世界；切换前校验分支历史链与锚点，之后的推演与章节保存写入当前所选存档。平台接口 `POST /api/branches/switch` 接受 `{"branch_id":"分支编号"}` 或 `{"branch_id":null}` 返回原世界。切换是当前服务会话的选择，不回滚、不合并、不改写原世界；也可在另一端口运行 `python platform.py --db "返回的分支存档路径" --port 8766` 独立打开。快照位于 `db/snapshots`，分支位于 `db/branches`。现有桌面压缩包尚未包含本轮分支切换代码。

指定其他存档或端口：`python platform.py --db "db/another.db" --port 8766 --new-world --seed 42`。创建操作不会覆盖已存在的数据库。服务默认只绑定本机 `127.0.0.1`，不暴露到局域网。

### 本地 Ollama 模型

平台默认连接本机 Ollama 的 `qwen2.5:7b`：

```bash
# 启动 Ollama 服务（若尚未运行）
D:/Ollama/ollama.exe serve
# 确认模型已安装
D:/Ollama/ollama.exe list
```

如需切换本机地址或模型，可设置环境变量后启动平台：

```bash
set LINGTU_LLM_URL=http://127.0.0.1:11434
set LINGTU_LLM_MODEL=qwen2.5:7b
python platform.py --new-world
```

`GET /api/model` 检查模型是否可用；人物对话使用 `POST /api/player/action`，请求体为 `{"action":"talk","target_id":村民编号,"words":"你想说的话"}`；写作草稿使用 `POST /api/chapters/suggest`，请求体为 `{"event_ids":[已发生事件编号],"direction":"写作方向"}`。模型接口被限制为本机 HTTP 地址，不会把世界资料发送到外网。

平台接口端到端检查：`python tools/platform_test.py`。

## 可交互切片（命令行）

无需重建或覆盖 `db/world.db`，默认使用独立存档 `db/play.db`：

```bash
python play.py init --seed 20261015
python play.py status
python play.py people
python play.py step --days 10
python play.py events
python play.py why 2
python play.py intervene relief 10     # 势力粮仓拨 10 单位到聚落
python play.py intervene reforest 10   # 消耗 10 单位薪柴恢复林木
python play.py step --days 30
```

`init` 拒绝覆盖既有存档；`step` 每次可推进 1~365 日，重新启动仍接着当前日期推进。
干预只能在当下发生，先追加不可变事件，再结算库存和环境变化；资源不足会拒绝。
`events` / `why` 可以查看近期事件及其因果链。运行 `python tools/play_test.py` 可验证整跑与分段推进逐条一致、干预的代价及历史守卫。

**当前边界**：这是浏览器可操作的本机平台 + 命令行切片，不是 Godot 像素客户端；已有玩家发起的本地模型对话与章节草稿，但尚无村民之间的 LLM 自主对话、原作导入或完整年度纪事。事件不可改写，但日常资源、生态和人口状态仍不是完整的事件流投影，不能仅由事件重建全部世界状态；数据库控制者也可以修改可变状态表。

## 快速开始

```bash
cd lingtu-zisheng

# 建库（12 张表）
python tools/build_schema.py --init --force

# 无干预推演 5 个游戏年
python run_p0.py --reset --seed 20261015 --days 600

# 多种子压力测试（验证不是只对一个种子有效）
python tools/stress_test.py --days 600 --seeds 12

# 历史完整性验证：防线在位？哈希链完整？过去能不能被复现？
python tools/verify_history.py

# 勘误演示：写错了历史怎么办（在副本上跑，不动真库）
python tools/demo_amend.py

# 确定性回归测试：同种子必须复现同一个世界
python tools/determinism_test.py --seeds 40

# P2 题材验收：切换题材产出结构不同的世界、调度无死角
python tools/genre_test.py

# P3 输出交互验收（离线引擎级）：叙事草稿只读、作者干预/入世、快照分支
python tools/p3_test.py

# 叙事后端验收（离线 mock）：本机默认 / 云端可选 / 隐私边界 / 优雅失败
python tools/llm_test.py

# 状态锚定验收：封印状态、检出并定位绕过事件的篡改、存档点重建
python tools/state_test.py

# 设定三态与网文导入验收：推断可提升/让位、规则抽取只读可确认
python tools/canon_test.py

# 聚落营造验收：满员才动工、有代价、事件可回溯、端到端自发加盖
python tools/housing_test.py

# 平台接口端到端（可选 --require-model 要求本机模型真实可用）
python tools/platform_test.py --offline

# 一键跑完全部验收测试（加 --quick 更快）
python tools/run_all.py
```

推演结束后会生成 `lingtu-zisheng-sim.html`（纪事报告）与 `out/chronicle.txt`（全文纪事）。
世界存在 `db/world.db` 里——**关掉程序重开，世界还是此刻的样子**。

常用参数：

| 参数 | 说明 |
|---|---|
| `--seed` | 随机种子。同种子必然复现同一个世界 |
| `--days` | 推演天数，1 日 = 24 tick。默认 600（5 年） |
| `--theme` | 题材标签 key，见 `data/genres.json`。默认 `lishi` |
| `--reset` | 清空重建世界 |
| `--quiet` | 不打印逐旬进度 |

## 引擎在做什么

P0 的核心是**让世界在没有干预的情况下自己往前走**，并且每一次变化都能被追问来由。

### 那条主链

```
采伐林木 → 植被覆盖率下降 → 猎物再生能力下降 → 狩猎产出降低
        → 粮食储备下降 → 民心下跌 → 人口外流
```

关键在**再生能力取决于上一环的存量**：林木少一分，猎物的再生就慢一分。
所以过度采伐不会立刻报应，而是在几十天后以猎获减少的形式找上门——这是涌现，不是脚本。

引擎里没有任何一条规则写着"砍树会导致人口流失"。

### 因果链

关键叙事事件可挂向上游原因（`cause_event_id`），`why` 可沿已记录的因果链追溯。
但日常资源消耗、生态连续变化等尚未逐步形成可回放事件，因此不能保证任意状态变化都能追溯到一条事件。

### 规则护栏

不是限制创作，而是防止推演在无人干预时走向两种退化态：**全灭**（世界没法往下讲）与**无限连锁**（一次砍树引爆全世界）。被拦截的变更不写进世界，只留记录——它们本身是"规则在起作用"的证据。

| 规则 | 作用 |
|---|---|
| G1 人口下限锁 | 聚落人口不得低于 5，触底进入衰退叙事态而非静默清零 |
| G2 因果链深度上限 | 单条链最多 4 层，超出降级为日志 |
| G3 资源再生约束 | 可再生资源不得为负；超采后再生速率按下调曲线递减 |
| G4 事件密度上限 | 单位时间内事件总数封顶，超出排队释放 |
| G5 势力存续保护 | 世界内至少保留 2 个活跃势力 |
| G6 死亡因果完整性 | 无因死亡一律拦截 |
| G7 设定一致性硬约束 | 生成内容不得与 `canon_fact` 中的既定事实冲突 |
| G8 历史不可改写 | 事件不可修改、不可删除、不可倒填 |

### 历史不可改写

这是引擎的底层法则，也是整个项目真实感的来源。

事件是**已然发生的事实**。一旦写下，就不可修改、不可删除——**哪怕作者也不行**。因为一旦允许改写，"世界自己长出故事"就退化成作者在幕后调参：看到结局不好就回去改中段，看到人物死了就复活。世界就不再是自己走的了。

四重保障，逐层收紧：

| 层 | 机制 | 拦住谁 |
|---|---|---|
| 1 | **数据库触发器** —— `event` 表的 `BEFORE UPDATE` / `BEFORE DELETE` 一律 `RAISE(ABORT)` | 挡住一切改写，包括有人拿 `sqlite3` 手敲 SQL |
| 2 | **存储层守卫** —— `Store.update/delete/bump` 对不可变表直接抛异常 | 挡住绕开 SQL、直接调接口的代码 |
| 3 | **哈希链** —— 每条事件指纹 = `sha256(前一条指纹 + 本条全部字段)` | 改动链上任何一个字符，从那条往后全部失配 |
| 4 | **历史锚点** —— 独立记录「共多少条 + 链尾指纹」 | 哈希链是向前链，砍掉尾巴仍自洽；这条专治截断 |

**为什么需要第 4 层**：哈希链是向前链——每条依赖前一条。删掉末尾几条，剩下部分的指纹依然全部吻合，链校验会通过。这个漏洞是在做篡改演练时被测出来的，不是设计时想到的。

**写错了怎么办**：**勘误，而不是回改。** 追加一条 `kind='correction'` 的事件指向被更正的那条，原记录原样留在链上——因为"当时的认知"本身也是真实发生过的事。报纸登更正启事，从不重印昨天的报纸。接口是 `Causality.amend()`。

**真想改变过去**：在某个历史点上另开一条时间线（`snapshot` 表，M107）。原时间线完整留存，新时间线独立演化。这是平行世界，不是篡改历史。

验证：

```bash
python tools/verify_history.py
```

它做五件事：拿真语句去撞防线、逐条重算哈希链、比对长度锚点与外部抄本、**用同种子把历史重放一遍**（两条历史必须逐字相同），最后故意删掉触发器、篡改一份副本，验证五种手法全部被检出。

### 确定性随机

同一个 seed 必须复现同一个世界，且随机值**不依赖调用顺序**——所有随机数由 `(seed, 维度..., 序号)` 哈希派生，而不是用有状态的随机对象。因此可以放心改动推演分支顺序而不破坏已有存档的可复现性。

**这条承诺曾经是假的。** 2026-10-15 的压力测试连跑三次得到 991 / 994 / 1004 条事件。追下去发现 `migration` 那条查询里藏了一个 SQL 的 `RANDOM()`——它绕过哈希派生，每次跑都挑中不同的人离乡。同时另有 4 处按数组下标取人的查询没有 `ORDER BY`，行序不保证。

修复后新增 `tools/determinism_test.py` 作为回归测试，它做两件事：同进程重复、以及**用不同的 `PYTHONHASHSEED` 起两个子进程重复**（后者能揪出依赖 Python 字符串 hash 或 set 迭代顺序的隐患，那类问题在同进程内看不见）。

```
40 个种子 × 600 日：40/40 逐条一致
3 种题材 × 900 日　：24/24 逐条一致
```

确定性不是洁癖。**它是历史验证的地基**——如果过去不能被重放，那"历史未被改写"就无从证明。

- **仍未做到「从创世起逐条重放重建」。** 当前是「可从封印点重建 + 篡改可检测 + 漂移可定位」，不是「从 genesis 开始完全由事件流重建」——后者要求每一次状态变更都作为事件完整记录（含 before/after），而生态/社会层的逐日微变更并非都有独立事件。这是后续要补的一环。
- **设定事实分三态**（`engine/canon_io.py`）：`canon`原作只读 ＞ `author`作者确认只读 ＞ `inference`推断（可改写、让位于上位）。硬事实判据与数据库触发器一致（`mutable=0` 或 `source='canon'`）；一致性校验的正/反相悖**只在硬事实间判定**，推断不参与、只给「让位」提示，并可一键提升为作者确认。（顺带修了一个旧 bug：「不是」此前被 `是` 抢先判成正向，正/反相悖永远检不出来。）
- **网文导入**（`engine/intake.py`）：从 TXT 原文用零依赖规则法抽取**候选**人物/地点（对话归属 + 显式命名 + 地名后缀，带次数与示例），**只读预览、不落库**，作者逐条确认后才写成 `author` 事实。抽取到的人物还可**一键建成具名世界角色**（`cast_characters`，只追加事件；具名个体与抽象人口分开统计，故不改人口与经济），并抽出**候选人物关系**（称谓/同现 → kind 恩/怨/爱 + 初步强度）写成角色间 `relation`（有向、双向各一条；需双方都已建角）。准确率有限——人名会漏抽低频、可能混入少量非人名；关系抽取比人名更易误判，只作候选，需作者剔除。
- 哈希链本身可被重算。若篡改者同时改事件、锚点与链，库内会自洽；此时唯一的见证是 `out/history.anchor` 这份**外部抄本**——它的可信度取决于它被存到了哪里。
- **确定性的承诺只在同一引擎版本内成立。** 引擎升级（如本轮加入 P2 题材机制）会改变同种子世界的事件流，因此旧存档不再逐条重放。仓库里的 `db/world.db`（柳坞境，77 事件）与 `db/play.db` 是 **P2 之前的存档**：其哈希链、锚点、外部抄本、篡改防线全部完好，但 `tools/verify_history.py` 的第 3 道「确定性重放」会判为不符——这不是历史被改，而是引擎换了。按项目约定，这两个正式存档不被自动覆盖/重建；若要用新引擎重放校验，请另存一份新存档（`python run_p0.py --db db/world-p2.db ...`）再对之验证。
- 外部锚 `out/history.anchor` 现在跟随它所见证的存档：只有默认存档（`db/world.db`）才写 `out/history.anchor`；用 `--db` 指定别的存档时，锚点写到该存档同目录，避免测试跑到一半覆盖了正式存档的外部见证。

## 怎么扩展

**加一个模块**：在 `modules.json` 的 `modules` 里追加，`id` 续号，选好 `cat` / `scope` / `phase`。若它是题材挂载的，还要在 `genres.json` 至少一个题材的 `on` 或 `simple` 里登记——否则 `validate.py` 会报孤儿。

**加一个题材**：在 `genres.json` 的 `genres` 里追加，填 `key` / `label` / `tags` / `on` / `simple` / `off`。

**改表结构**：改 `data/schema.json`，重跑 `build_schema.py --init --force`。

**让一张表变成不可改写**：在 `data/schema.json` 对应表里加 `"immutable": true` 和 `"immutable_reason"`，重跑 `build_schema.py` —— 数据库触发器会自动生成，`Store` 的守卫也会自动生效（不可变表清单是运行时从 `schema.json` 读的，不需要改代码）。

**调推演参数**：节律与护栏改 `spec.json`；生态与生产参数在 `engine/ecology.py` 顶部（`FARM_BASE`、`HUNT_GAME_COST`、`GAME_REGEN`、`WOOD_FOREST_COST` 等）；社会参数在 `engine/society.py` 顶部。

**任何一次改动之后，先跑 `tools/validate.py` 和 `tools/stress_test.py`。** 它们是这个项目的护栏。

## 版本沿革

### v1.0 规格修订

原始需求清单存在三处结构性问题，已修复：

1. **编号体系失效** —— 原文自称 001~134 连续编号，实际列出 135 条且第 70 条重复占用；096~126（31 条）与 127~134（8 条）全部是 001~095 已有模块的重新表述。去重后独立模块 94 个，重复 41 条。现重编为 `M001~M107`，原文编号存入 `src` 字段。
2. **24 个孤儿模块** —— 原题材调度表从未引用它们（M073~M084 整块阵亡，玄幻题材没有功法/灵气/妖兽/丹药/宗门）。逐题材补齐挂载后归零。
3. **模糊规则 + 数值面板张力** —— 三条不可执行规则落成配置；"无 RPG 数值"与成长体系的冲突用序数化 `power_scale`（碾压/压制/势均力敌/不敌/悬殊）解决。

同时补入 **13 个引擎内核模块**（M095~M107）：世界时钟、因果链、事件导演、规则护栏、世界种子、设定导入、一致性校验、货币体系、供需总账、生命周期、叙事生成、作者干预、存档分支。没有这一层，前面 94 个模块只是名词表。

### v1.1 历史不可改写

**事件产生了，就不能修改。** 在此之前，"事件不可改"只是一条约定——代码里碰巧没有写过 `UPDATE event`，但没有东西阻止别人写。v1.1 把它落成四重硬约束，并配套一个能证明它有效的验证器。

过程中发现两个真实缺陷，都是被测试逼出来的，不是设计时想到的：

1. **哈希链防不住尾部截断。** 链是向前链，砍掉末尾几条后剩下部分的指纹依然自洽。补上独立的历史锚点（条数 + 链尾指纹）后才堵住。
2. **引擎其实不确定。** 同一压力测试连跑三次得到 991 / 994 / 1004 条事件。根因是 `migration` 查询里的 SQL `RANDOM()`，以及 4 处没写 `ORDER BY` 就按下标取人的查询。这条比第一个严重得多——它让"历史可被重放"这个立论基础本身失效了。
